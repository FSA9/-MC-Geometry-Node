# 视口输入与屏幕切换

本目录管理一个玩家游戏输入所有者及一个编辑相机飞行所有者。显示同一 GAME 帧的多个视图不会各自获得玩家输入；玩家控制和编辑飞行通过释放对方实现互斥。原版键鼠状态、鼠标抓取、屏幕切换、世界/玩家有效性检查都在 Minecraft 客户端线程执行。

| 文件 | 职责 |
| --- | --- |
| `GameViewportInput` | 视图可见性与工作区阻塞状态、玩家捕获/释放、Escape、死亡/睡眠/原版屏幕期间保留和恢复工作区，以及向输入 mixin 提供有作用域的 Screen 视图。 |
| `EditViewportFlightInput` | 编辑相机飞行捕获、物理按键与鼠标导航，按帧更新时间，验证 owner/相机/世界后失效释放，并交接按住菜单键。 |
| `EditViewportFlightBindings` | 捕获会话冻结的快捷键配置，逐事件根据物理按键评估组合；不在会话中任意切换配置。 |
| `ViewportInputDispatch` | 客户端线程内立即运行释放操作，其他线程派发；同时管理可取消的待捕获请求。 |
| `ViewportMenuHold` | 飞行交还鼠标后仍按住的菜单键及其取消/释放交接。菜单回调在客户端线程执行，具体 UI 由宿主适配。 |

## 请求、取消和释放

UI 激活点击在释放之后提交 `requestCapture`。捕获请求入客户端队列，真正执行前再次检查视图仍可用、工作区未阻塞、窗口激活、世界/玩家状态及 owner 身份。`CaptureRequests` 按请求实例原子接受，后一次点击替换待处理请求；取消按 owner 对象身份判断，关闭其他区域不会取消当前请求。

关闭、隐藏或阻塞区域时既取消待接受请求，也释放已安装所有者。客户端线程中的嵌套释放必须立即执行，不能全部改成 `Minecraft.execute`：后者可能把旧会话清理排到新捕获之后，错误释放新所有者。UI 线程释放仍通过客户端队列执行，使已被接受但尚未安装 owner 的捕获也按顺序完成清理。

释放玩家捕获时清理按键、鼠标和蓝图输入状态，并停止仍在进行的方块破坏/物品使用；飞行捕获清理自己的按键、菜单状态和导航状态。窗口失焦、世界或相机失配、overlay 和屏幕切换等有效性变化通过现有验证路径释放，不能仅清空 UI 标志。

## 宿主与原版屏幕

`ViewportHostPolicy.snapshot(screen).workspace()` 判断可承载视口的工作区。`replacesRetainedWorkspace()` 决定新屏幕是否替换保留的工作区；它与“本身是工作区”独立。具体 MuiScreen/MainUI 分类在 [integration/game](../../../integration/game/README.md) 完成，这里只消费能力。

玩家输入活跃时临时打开原版屏幕，会保留工作区，按正常 `setScreen` 参数边界在关闭后恢复；死亡/睡眠也遵循保留与原版流程。进入另一个由宿主管理的屏幕则可丢弃旧工作区。Escape 的按下、重复和释放归属，以及过时原版屏幕的 `onClose` 防护，都用于避免恢复后再次关闭工作区。

`screenForGameInput` 只供指定输入调用点使用，不能据此全局改写 `Minecraft.screen`。具体 UI 的移除/焦点变化继续通过请求和释放入口接入，不能从 UI 线程直接调用原版抓鼠标或修改 KeyMapping。
